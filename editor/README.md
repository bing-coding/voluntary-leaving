# 《自愿离校》文案编辑模式

编辑入口是站点下的 `editor.html`。正常游戏入口仍是 `index.html`。本文件说明使用和交接方式，不代表测试站点已经部署。

编辑器复用游戏的实际页面，提供 **168 个审校场景**，涵盖开场、业务系统、复学前后、检索结果、弹窗、短暂提示、复核与回转、七种结局及其文案变体。场景按照不同可见文案编排，不是所有变量组合的穷举；可以在交互模式中进一步检查。

## 策划如何使用

1. 从左侧目录选场景，或搜索系统、状态、结局名称。无需登录或通关。
2. 在中间页面点击文字。右侧会显示原文、修改稿和备注；输入修改稿后，即时更新页面预览。
3. 难以点中的文字，可以从右侧「本页文字」选择。这里也列出按钮提示、输入框说明、图片说明和部分表单显示文字。
4. 用「桌面 / 手机」与缩放选项查看排版。编辑模式会展开折叠内容；需要操作游戏控件时，点「切换到交互」，完成后点「返回编辑」。
5. 「重置场景」会回到该场景的初始状态，已保存的编辑稿保留。「恢复原文」清除此条修改及备注；「撤销上次修改」撤销本次页面会话中的编辑操作。
6. 检查完一个场景后勾选「本场景已审」。未改字也可以标记已审。左侧支持筛选未审和已修改场景。
7. 从「修改记录」检查原文与改稿，最后使用「导出修改包」交付 JSON 文件。可同时导出 Markdown 可读清单，方便讨论；**JSON 是导入和合稿依据**。

场景链接带有 `#场景标识`，可以分享具体审校位置；链接不包含本机草稿，发链接时仍需一并交付修改包。

## 保存、备份与交接

草稿自动保存在**当前浏览器、当前站点、当前基准版本**的本地存储中。它不是云端协作文档，不会自动同步给开发者；换设备、换浏览器、换测试域名或清除浏览器数据后，原草稿可能不可见。

- 每轮工作结束、交接或换设备前，导出 JSON 修改包并保留备份。
- 接续工作时，在相同基准的编辑器中选择「导入修改包」。导入会保留本机已有修改，不会用导入包中缺少的条目删除本地工作。
- 同一条修改存在不同版本时，整个导入会被拒绝，不会静默覆盖。保留双方 JSON，交由开发或负责人确认。
- 不同游戏基准的修改包不能直接导入。开发更新代码后，应先核对旧修改包，再发布新的审校基准。
- 若出现本地保存失败提示，立即导出；此时修改可能只保存在当前页面内存中。

**当前预览修改以场景和文字位置为范围。** 相同原文在另一个场景出现时，不会被盲目替换。右侧「定位与合稿信息」显示源码候选；即使命中同一源文件，也需要开发确认是否应该共用同一改稿。需要统一修改人名、术语或按钮时，请在备注写明影响范围。

## 文案和图片的边界

普通页面文字、可访问名称及输入提示可以即时预览。图片内的文字是图像像素：选中图片后，请在修改稿或备注中写明**所在区域、原字、替换文字和修改意图**。编辑器仅记录改图要求，**不会重绘图片**。

编号、人名、日期、IP、邮箱和关键证词可能参与解谜。风险提示用于提醒检查关联位置，不会阻止提出修改。特别注意：审核时间早于申请时间、原话与归档摘要不同，可能正是游戏的线索；对这些内容的修改应说明是否保持原有推理关系。

动态文字会带入证据数量、人物、当前节点等变量。编辑器保存的是选中场景的实际显示结果，开发合稿时需要保留变量，而不是把该场景的示例数字写死。

## 开发如何接收修改包

导出的每条记录包含原文、修改稿、类型、场景、页面定位、备注和源码候选。候选基于原文片段匹配，可能有多处或没有精确匹配；它不是可直接执行的代码补丁。

先在游戏项目根目录运行只读核对工具，无需安装依赖：

```bash
node editor/check-package.cjs /path/to/文案修改包.json
```

也可以指定另一个待核对的项目目录：

```bash
node editor/check-package.cjs /path/to/文案修改包.json --root /path/to/voluntary-leaving
```

工具向标准输出打印 JSON 报告，**不会修改任何游戏文件，也不会自动改写 JavaScript**。检查内容包括：

- 修改包格式与项目标识。
- 修改包、`editor/sources.js` 源码快照和本地源码的 SHA-256 基准是否一致。
- 每个源码候选的原文、偏移、行号和文件哈希是否仍匹配。
- 不同场景是否向同一个源码候选提交了不同改稿。
- 没有精确源码位置的动态文字、多个候选和图片修改要求。

退出码 `0` 表示核对通过、可以开始人工合稿；`1` 表示基准变化或候选冲突等问题；`2` 表示参数、文件或修改包格式无效。即使核对通过，仍要确认 JavaScript 字符串转义、HTML 结构、动态字段、跨场景共用关系及解谜逻辑。

建议按下面的次序合稿：先解决改稿冲突和统一术语，再修改正式文案源，处理图片要求，运行现有测试，最后回到关键路线与手机尺寸检查。不要对源码做无上下文的全局字符串替换。

## 本地运行与维护

在项目根目录启动静态服务，再打开 `http://127.0.0.1:8765/editor.html`：

```bash
python3 -m http.server 8765
```

文件职责：

| 文件 | 作用 |
| --- | --- |
| `editor.html` | 文案工作台入口 |
| `preview.html` | 使用真实游戏脚本的隔离预览页 |
| `editor/scenes.js` | 场景与状态目录 |
| `editor/preview.js` | 页面定位、文字和属性预览、图片批注入口 |
| `editor/patches.js` | 修改包校验、草稿合并与导出 |
| `editor/sources.js` | 生成的正式源码快照和基准哈希 |
| `editor/check-package.cjs` | 只读交付核对工具 |

正式源码发生改变后，重新生成审校快照，再交付新版本：

```bash
node editor/build-sources.cjs
node editor/build-sources.cjs --check
for f in scripts/*.test.js editor/*.test.js; do node "$f" || exit 1; done
```

场景目录中的短提示与风险日志使用固定显示样例。修改这些正式文案时，应同步场景样例；场景测试会检查固定反馈是否仍被覆盖。编辑器本身不写入正常游戏存档，策划的修改稿也不会自动发布到正式游戏。

测试部署应从编辑分支产生独立预览地址，策划访问该地址下的 `editor.html`。将代码合入正式分支与发布正式游戏，属于后续独立的合稿和发布步骤。
